# DocuMaster 개발 방향

작성일: 2026-10-01 · 상태: 개발 계획(미구현 기능 포함)

개발 세션에서 참고한다. 문서·발표 생성 에이전트의 실행 입력에는 싣지 않는다. 실제 구현 범위는 각 작업에서 정하고, 완료한 단계에는 검증 결과와 커밋을 기록한다.

## 1. 목표와 현재 기반

생성한 문서와 검증 자료를 축적하고, 검색·수정·재사용할 수 있는 시스템으로 발전시킨다. 우선 대상은 로컬 단일 사용자다.

현재 웹앱은 Next.js → FastAPI → 기존 Claude 오케스트레이터 구조다. SQLite에는 프로젝트·실행·이벤트·자료·작업물·설정·사용자 응답·대기열을 저장한다. 작업물 버전 번호와 실행 모델 설정 스냅샷도 있다. 이번 계획은 이 기반 위에 검색·버전 관계·근거 추적을 확장한다.

## 2. 유지할 계약

- 팀·역할·검증·게이트는 `../../CLAUDE.md`와 담당 절차서가 정한다. 웹앱은 실행 요청·상태·사용자 선택을 관리한다.
- 실행 엔진은 기존 `claude`와 테스트용 `fake`를 유지한다.
- `00~07`, 상태·기록, 원문, 최종 PDF는 파일을 원본으로 둔다. 사실·구조의 권위는 기존 생성 계약을 따른다.
- DB에는 검색 색인·파일 관계·운영 기록을 둔다. 지침은 Git으로 관리하며, DB 설정으로 사실성·검증 게이트를 덮어쓰지 않는다.
- 검색 결과와 과거 검증 자료는 새 작업의 참고 후보로 취급한다. 새 작업에서 사용할 사실은 해당 작업의 검증·채택을 거친다.
- 개발 변경·검사·커밋 규칙은 `../../AGENTS.md`, 웹앱 구현은 `../../webapp/README.md`와 해당 폴더 지침을 따른다.

## 3. 단계별 개발

### 0단계 — 데이터 확장 기반

- 스키마 변경 이력과 순차 마이그레이션을 관리한다.
- DB와 문서 파일의 대응을 보존하는 백업·복원 절차를 만든다. 실행 중 백업의 일관성 기준을 정한다.
- 파일 기반 색인과 DB에만 있는 사용자 기록을 구분한다. 태그·메모·채택 이력은 색인 재생성 때 보존한다.
- 완료: 기존 버전 DB의 사본으로 이관·복원·색인 재생성을 검증하고, 파일 누락을 탐지한다. 실제 사용자 DB로 테스트하지 않는다.

### 1단계 — 문서 라이브러리와 버전 관리

- 기존 작업·최종본을 제목·본문·글 유형·날짜·태그로 찾는다.
- 같은 문서의 초안·수정본·최종 채택본을 묶고, 원래 요청·참고자료·수정 이유를 연결한다.
- 버전별 파일 해시와 입력 관계를 기록한다. 덮어쓴 파일의 과거 내용을 메타데이터만으로 복구할 수 있다고 표시하지 않는다.
- 기존 자료는 읽기 전용으로 색인한다. 가져온 프로젝트의 수정 기능은 별도 복제·새 작업 정책을 정한 뒤 제공한다.
- 완료: 두 예시 문서(건설업 가이드·최저임금 해설)를 검색하고, 버전과 원본을 열 수 있다. 재색인·서버 재시작에도 중복과 사용자 기록 유실이 없다.

### 2단계 — 검증 근거 라이브러리

- 채택된 `05`에서 주장·출처·기준일·단위·범위·판정·조건을 색인한다.
- 원래 작업 ID, 파일 버전·해시, 절 위치를 보존해 원문으로 돌아갈 수 있게 한다. `S01` 같은 출처 ID는 작업 간 공통 ID로 사용하지 않는다.
- 같은 출처의 서로 다른 주장·판정 이력은 합치지 않는다. 조건이 다른 수치는 별개로 남긴다.
- 재사용 시 적용 시점·범위·원문 변경을 확인할 항목으로 제시한다. 고정 유효기간 하나로 모든 사실의 최신성을 판단하지 않는다.
- 완료: 주장 하나에서 출처와 검증 버전을 추적할 수 있다. REMOVE가 채택 사실로 검색되지 않고, CAUTION의 조건이 유지된다. 검색 자료가 검증 없이 집필 입력으로 들어가지 않는다.

### 3단계 — 영향 범위에 따른 수정 실행

- 변경 요청을 편집, 문장·구조, 독자·목적, 사실 갱신으로 구분한다.
- 웹앱은 요청과 입력 버전·영향 단계를 기록하고, 로이드는 기존 계약에 따라 재개 범위와 검사를 판단한다.
- 편집은 렌더, 문장·구조는 집필·내용 검사, 독자·목적은 기획 영향 검토, 새 사실은 조사·검증 갱신으로 연결한다. 이는 기본 분류이며 실제 영향에 따라 범위를 넓힌다.
- 검증 라운드·기획 개정 규칙은 기존 지침을 따른다. 새 작업 이름으로 라운드를 우회하지 않는다.
- 완료: fake 실행에서 수정 종류별 입력·재개·검사 경로를 확인한다. 이전 최종본을 보존하고, 변경된 입력에 의존하는 결과가 자동 재채택되지 않는다.

### 4단계 — 품질 기록과 편집 선택

- 실행별 지침 버전·도구 버전·입력 해시와 모델 설정을 연결한다. 미커밋 변경이 있으면 커밋 번호만으로 재현 가능하다고 표시하지 않는다.
- FACT·LOGIC·INTERNAL·DEPTH·DUP, 렌더 문제와 수정 사유를 모아 반복 문제를 찾는다. 이 범주는 doc-finish의 정의를 참조한다.
- 소요 시간·재시도·확인 가능한 비용을 기록한다. 공급자·세션별 집계 범위를 표시하고 누적 비용을 중복 합산하지 않는다. 확인 불가를 0으로 저장하지 않는다.
- 기본 가독성·출처 체계는 유지하고, 분량·독자의 읽는 방식에 따라 표지·장 시작·요약·체크리스트 배치를 선택하도록 확장한다. 7개 글 유형과 디자인을 일대일로 고정하지 않는다.
- 디자인 설정에는 렌더러 지원 범위와 버전을 둔다. 문서규격과 변환기를 함께 수정한다.
- 완료: 반복 오류와 실행 조건을 조회하고, 서로 다른 길이의 문서로 편집 선택과 PDF 품질을 확인한다.

## 4. 데이터 설계 기준

아래는 개념 단위이며 테이블 이름은 구현 시 결정한다.

| 데이터 | 핵심 관계 |
| --- | --- |
| 문서 색인 | 프로젝트·원본 파일·유형·태그·검색 본문 |
| 문서 버전 | 이전 버전·수정 요청·파일 해시·채택 기록 |
| 근거 | 주장·출처·조건·판정·원래 검증 버전 |
| 수정 실행 | 요청·입력 버전·영향 단계·결과 버전 |
| 품질 기록 | 실행·검사 종류·문제 위치·해결 상태 |
| 사용자 프리셋 | 독자·목적·분량·편집 설정·설정 버전 |

SQLite를 우선 유지한다. 전문 검색은 FTS5를 후보로 실제 한국어 질의의 검색 품질을 검증한다. 검색 정확도·데이터량·동시 쓰기 요구를 측정한 뒤 벡터 검색이나 서버형 DB 도입을 판단한다.

## 5. 다음 작업의 범위

첫 개발 묶음은 0단계 기반과 1단계 문서 라이브러리다. 원본을 수정하지 않는 색인 → 검색 API → 목록·필터·버전 화면 순으로 구현한다. 범위가 크면 독립적으로 검증·커밋할 수 있는 단위로 나눈다.

근거 자동 재사용, 다중 사용자·조직 권한, 여러 실행의 동시 처리, 엔진 교체는 이 첫 묶음에 포함하지 않는다. 각 단계의 완료 기준을 통과한 뒤 다음 단계로 진행한다.
